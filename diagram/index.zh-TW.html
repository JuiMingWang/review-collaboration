確認完整送審包、決定是否補件、核准最終決策，或在 cap 到達時裁決。

Step 0 → Step 5：主流程

STEP 0

選定範圍；決定新建或恢復

  • 明確相同：恢復既有 review_id。
  • 明確不同：建立新案。
  • 重疊或證據不足：才請使用者選擇。
  • 關鍵歷史缺失或矛盾：停止並回 manual_recovery，不猜、不重送。
讀：active／history 索引與 state　出：路由結果、依據、review_id 或停止原因
↓
STEP 1

把原始討論整理成可審查內容

  • 固定覆蓋：問題、目前結論、限制、關鍵前提與查證狀態、替代方案、未知、排除內容與敏感限制。
  • 每次低成本搜尋 Skill 自管 history；只在找到候選時深入讀。
  • 匿名化去除身分與權威暗示，但保留會改變決策的限制與證據。
不承諾：摘要等同完整逐字稿；缺件時由後續 MATERIAL_REQUIRED 安全補充。
↓
STEP 2

產生 checklist，讓使用者確認完整 package

  • 先重建角色、輸入、輸出、狀態、交接與外部依賴，再檢查目標、完整性、可行性、安全性、可逆性與成本。
  • Codex 同時收到固定開放式指令，不被 checklist 上限綁住。
  • 確認後建立 immutable Markdown package，以完整 SHA-256 識別；任一 byte 改變都需新 hash 與重新確認。
恢復邊界：confirm-package 成功建立 active state 後，才開始承諾跨 Session 可恢復。
↓
STEP 3

Controller 呼叫 adapter；adapter 呼叫 Codex

  • 沒有 runtime Subagent，也沒有 manifest。
  • 每次 Codex call 使用唯一 operation_id；同一 round 可有多次 operation。
  • 先保存 launch intent，再啟動 Codex；看到 thread.started 立即保存 thread ID。
  • 只有 process、exit code、completion event、schema 與 hash 全部可信，才接受結果。
prepared → launch_intent_saved → thread_captured → result_validated → state_committed
↓
STEP 4

依結構化結果協商，不解析自由文字

  • CONSENSUS：沒有 open issue、new issue 或 pending material。
  • ISSUES_RAISED：Producer 對每個 issue 選 Fix 或 Pushback；Codex 回 FIX_ACCEPTED／FIX_INSUFFICIENT 或 CONCEDE／MAINTAIN。
  • MATERIAL_REQUIRED：非 final，同一 round 補件後再取得 final outcome。
  • 只有 final outcome 增加 completed round；到 cap 後腳本禁止建立 N+1。
保存：operation receipt、raw result、Producer response、material、每輪 immutable ledger；ledger 自帶 package hash。
↓
STEP 5

確認最終決策；建立 history 與 handoff

  • final package 綁定最新 ledger、issue 處置、條件與證據；使用者核准綁定確切 hash。
  • 首版不修改 target。handoff 說明後續是否需要 implementation／user action，純決策可標示無後續動作。
  • history 實體保存所有永久引用；最後寫入並驗證 completion.json 才算 ended。
  • ADR／review-log 是選配；active／TEMP 清理失敗只留下 warning。
正常結束：consensus-finalized　其他：user-arbitrated-closed／abandoned／superseded

詳細控制流圖（Step 0 → Step 5 全展開，含泳道與資料標註）

上面「主流程」是第一次理解用的摘要，只畫得出「大致會經過這幾步」；這張圖是同一套 v1 設計的完整版本——Step 0 的四向路由、Step 2 的確認回圈、Step 4 三種 outcome 各自的迴圈與 cap 判斷、使用者仲裁、Step 5 的核准與收尾，以及中斷／manual_recovery_required 安全分支，全部畫成節點與連線，並用角色泳道取代文字描述「誰負責」。下面既有的「三條分支」「中斷後怎麼判斷」「五個入口」三節內容，這張圖已經涵蓋；保留那三節是給只想查表、不想看全圖的人用，兩邊互為對照，不是互相取代。

使用者 Producer／Controller PowerShell adapter Codex Reviewer 菱形＝需要判斷的決策點（旁邊文字＝判斷依據） 虛線框／側欄＝設計決定但尚未經腳本或 E2E 驗證（含全部 manual_recovery_required 分支） 圓角虛線小標籤＝資料／artifact（hash、state、receipt…）

圖依 Step 切成幾個分頁，每頁盡量一次顯示完整內容，不用一直捲動；「全圖（可捲動）」分頁保留原本的完整視圖，方便追蹤跨分頁的連線（例如側欄 manual_recovery_required → terminate）。

怎麼讀決策依據：「Step 0B 案件路由」的依據是 Producer 對主題／範圍的語意比對，腳本本身不判斷語意，只認 Producer 送進來的路由結果；「N ＝ cap？」的依據是完成 final outcome 的輪數是否已達使用者核准的絕對上限（不是嘗試次數，MATERIAL_REQUIRED 的同輪補件不計入）；「使用者核准（綁定 exact hash）？」的依據是使用者是否認可 final_package_hash 對應的完整內容，不是口頭同意結論。

三條真正會回圈或停下的分支

MATERIAL_REQUIRED

缺少特定材料

  • 建立 append-only request。
  • provide_material_or_unavailable：使用者／Producer 一次決定提供已整理 excerpt（每案最多三段），或標 unavailable。
  • 回同一 round；不改 base package、不增加 round。
ISSUES_RAISED

問題仍未解決

  • N < cap：Fix／Pushback 後再送下一 final round。
  • N = cap：停止，等使用者仲裁。
  • 新增實質輸入：明確增加 cap，回 Step 1–2 建立新完整 package 並重新確認。
CONSENSUS

Reviewer 已同意

  • Producer 編譯 final package。
  • 使用者確認 exact hash。
  • 產生 handoff、history 與 completion marker。
  • 審查結束，但實作是否完成另看 handoff。

中斷後怎麼判斷下一步

看到的可靠證據安全動作禁止事項
尚未完成 package 確認重新整理並讓使用者確認。不得宣稱能從準備中間點恢復。
只有 prepared，且可證明尚未 launch安全重跑同一 operation。不能只靠「沒有結果」推論未啟動。
已有 launch intent，但是否啟動不明查 PID、events、thread；仍不明就 manual_recovery。不得盲目重送。
已有 thread ID，沒有可信 final result依保存的 events／result 狀態 resume 同一 thread。不發明 recap 狀態，也不保證 Reviewer 能回報過去是否完成。
result 已驗證，state 尚未 commit只做本地冪等 commit。不得再次呼叫 Codex。
history 只有部分檔案，沒有有效 completion marker從 active immutable artifacts 冪等補齊並驗 hash。不得標示 ended 或先刪 active。
completion marker 有效視為核心已結束；可重試選配整合與 cleanup。cleanup warning 不得把案件倒退回 reviewing。

Review Collaboration: How It's Designed to Run

A process that hands the Producer's discussion conclusion to a Codex Reviewer to find fault with, negotiate over, and preserve the resulting decision on. The first version implements only Claude Producer／Controller → Codex Reviewer; once review completes it produces a handoff, but never modifies the reviewed target directly.

Read this first: the design described below has been implemented and passed one real end-to-end verification (confirm-package → real call to Codex → correctly written back to the ledger, including verification that the working-directory-isolation mechanism itself works). Still early-stage with light usage so far — treat it as "verified to work, but hasn't yet accumulated much real-world mileage," not as a paper design, but also not yet a battle-tested mature tool.

Four Roles, One Line of Responsibility Each

User

Confirms the full review package, decides whether to supply requested material, approves the final decision, or arbitrates once the cap is reached.

Claude Producer／Controller

Prepares the content, verifies and anonymizes it, produces the checklist, judges Fix／Pushback, and submits the semantic input to the script.

PowerShell adapter

The only role that writes state — owns hashing, locking, revisions, the Codex call, schema, recovery, and archiving.

Codex Reviewer

Independently finds problems, requests material, judges whether a Fix is sufficient, and replies CONCEDE／MAINTAIN to a Pushback.

Five States Are the Whole Case's Lifecycle, Not Step 0's Five Sub-Stages

preparing

Step 0–2. No cross-session recovery is promised before confirmation.

confirmed／recoverable

The full package has been hashed and durable active state established.

reviewing

Codex calls, Fix／Pushback, and same-round repairs.

waiting-user

Only for material requests, re-confirmation, final confirmation, arbitration, or a recovery decision.

ended

history's completion.json is verified; does not imply the target has been modified.

Step 0 → Step 5: Main Flow

STEP 0

Scope the case; decide new vs. resume

  • Clearly the same: resume the existing review_id.
  • Clearly different: create a new case.
  • Overlapping or insufficient evidence: only then ask the user to choose.
  • Critical history missing or contradictory: stop and return manual_recovery — never guess, never resend.
Reads: the active／history index and state　Outputs: the routing result, its basis, and either a review_id or a stop reason
↓
STEP 1

Turn the raw discussion into reviewable content

  • Fixed coverage: problem, current conclusion, constraints, key assumptions with verification status, alternatives considered, unknowns, excluded content and sensitive constraints.
  • A cheap search of the skill's own self-managed history every time; only reads deeper when a candidate is actually found.
  • Anonymization strips identity and authority cues, but keeps whatever constraints and evidence would actually change the decision.
Not promised: that the summary is equivalent to a full verbatim transcript — gaps are safely filled later via MATERIAL_REQUIRED.
↓
STEP 2

Produce the checklist; get the user to confirm the full package

  • First rebuilds roles, inputs, outputs, state, handoff, and external dependencies, then checks goal alignment, completeness, feasibility, safety, reversibility, and cost.
  • Codex also receives the fixed open-ended instruction at the same time — it is never bound by the checklist's ceiling.
  • Once confirmed, an immutable Markdown package is created, identified by its full SHA-256 — any single byte changing requires a new hash and re-confirmation.
Recovery boundary: cross-session recoverability is only promised once confirm-package has successfully established active state.
↓
STEP 3

Controller calls the adapter; the adapter calls Codex

  • No runtime Subagent, and no manifest.
  • Every Codex call uses a unique operation_id; a single round can involve multiple operations.
  • The launch intent is saved before Codex starts; the thread ID is persisted the instant thread.started is seen.
  • A result is only accepted once the process, exit code, completion event, schema, and hash are all trustworthy.
prepared → launch_intent_saved → thread_captured → result_validated → state_committed
↓
STEP 4

Negotiate off the structured result — never parse free text

  • CONSENSUS: no open issue, new issue, or pending material.
  • ISSUES_RAISED: the Producer picks Fix or Pushback for every issue; Codex replies FIX_ACCEPTED／FIX_INSUFFICIENT or CONCEDE／MAINTAIN.
  • MATERIAL_REQUIRED: not final — the same round continues to a final outcome once material is supplied.
  • Only a final outcome increments completed round; once the cap is hit, the script refuses to create round N+1.
Saved: the operation receipt, raw result, Producer response, material, and an immutable ledger per round; the ledger carries its own package hash.
↓
STEP 5

Confirm the final decision; build history and handoff

  • The final package binds the latest ledger, issue dispositions, constraints, and evidence; the user approves by binding an exact hash.
  • The first version never modifies the target. The handoff states whether follow-up implementation／user action is needed — a pure decision can mark no follow-up at all.
  • history physically preserves every durably-referenced artifact; only writing and verifying completion.json counts as ended.
  • ADR／review-log are optional; a cleanup failure on active／TEMP leaves only a warning.
Normal end: consensus-finalized　Other: user-arbitrated-closed／abandoned／superseded

Three Branches That Actually Loop or Stop

MATERIAL_REQUIRED

Missing specific material

  • Creates an append-only request.
  • provide_material_or_unavailable: the user／Producer decides, once, to supply a prepared excerpt (at most three per case) or mark it unavailable.
  • Returns to the same round; the base package is unchanged and round count doesn't increase.
ISSUES_RAISED

The issue isn't resolved yet

  • N < cap: after Fix／Pushback, the next final round is sent.
  • N = cap: stop, wait for the user to arbitrate.
  • Adding substantive input: explicitly raises the cap, returns to Step 1–2 to build a new full package and re-confirm.
CONSENSUS

The Reviewer has agreed

  • The Producer compiles the final package.
  • The user confirms the exact hash.
  • The handoff, history, and completion marker are produced.
  • The review has ended, but whether implementation is complete is a separate question decided by the handoff.

What You Can Trust Right Now／What You Still Can't

You can trust

  • Step 0–5's design choices have been confirmed by the user, and landed in the formal SKILL.md on 2026-08-17.
  • The first version's roles, data ownership, stop points, and recovery principles are closed.
  • handoff-only, the five commands (status／confirm-package／advance／submit／terminate), and artifact closure are implemented — not merely a target.
  • The PowerShell CLI, JSON schemas, and history bundle all exist; 92 automated tests (Pester, against a fake reviewer) all pass.
  • At least one real Codex call has been verified: confirm-package → advance → correctly written back to the ledger, including that the working-directory-isolation mechanism itself actually works.
  • "Verified" and "design inference" must still be described separately — the two items below are exactly what's still "design inference."

You still can't trust

  • That a Codex thread can always resume after a real interruption (e.g. the flow being force-killed mid-way) — only a cleanly-completed single round has actually been verified; no genuine mid-flight interruption has been simulated yet.
  • That multi-round Fix／Pushback, cap arbitration, and the material-request loop have been walked through a full E2E with the real Codex — this logic is covered by 92 automated tests (against a fake reviewer), but only the simplest single-round path has actually been run against the real Codex; multi-round, cap-reached, and material-request paths against the real reviewer remain unverified.
  • That any target has been safely modified — the first version simply never modifies the target, which this progress doesn't change either way.

What the User Should See When Approving Step 5

"The review decision is complete; the approval is bound to this version, the handoff has been saved, and no target has been modified."

If the handoff marks follow_up_required: true, it must also state: which implementation or user action is still pending, and which target baseline needs re-checking before that follow-up work begins.

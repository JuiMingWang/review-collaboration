# 審查清單只當「下限」，不當「上限」

**Status**: accepted

審查協作原本設計成：產出者針對這次討論的主題，現場擬一份「這次審查該檢查哪些面向」的清單，送給審查者前先給使用者確認。但這個設計本身有一個結構性風險：清單是**產出者**擬的，而產出者正是討論當下可能存在知識盲區的那一方——如果清單只由產出者決定內容，清單很可能只是把產出者自己的思考範圍換個形式重新交給審查者，審查者查得再仔細也查不出清單本身沒列到的角度，找審查者的初衷（借助不同模型製造真正視角差異）就被這份清單架空了。

因此決定：送給審查者的審查請求，一律**同時**包含兩個部分，缺一不可：

1. **清單（下限）**：產出者依討論主題現場擬的具體檢查項目，負責解決「審查者明明知道、但當下沒被提醒去檢查」的疏漏。
2. **開放式跳脫指令（上限破除，固定條款）**：明確要求審查者不要被清單限制住，主動思考清單完全沒提到、但可能更關鍵的角度或解法。這條指令**內容必須完全通用、不涉及本次討論的具體主題**，且是每次審查請求的標準固定條款，不由產出者臨場決定要不要加——因為如果這條指令也是產出者臨場決定，那它同樣可能因為產出者當下的盲區而被漏加，等於沒解決問題。

第 2 點之所以能打斷「產出者的盲區污染清單」這個遞迴，是因為它完全不帶具體內容（不提到耦合、效能、安全等任何字眼），只是要求審查者跳脫清單本身——沒有具體內容的指令，就不會遺傳產出者的思考侷限。

## Considered Options

- **只給清單，不給開放式指令**：全面性有保證的部分只限於清單內容，清單以外的盲區完全查不到，等同於沒解決本文件開頭提出的風險。
- **只給開放式指令，不給清單（純通用指示）**：不會限縮審查者，但失去清單「強制系統性掃描已知重要面向」的效果，容易漏查明明重要但當下沒被提醒的項目。
- **兩者並行，開放式指令為固定條款（採用）**：清單顧「已知重要但容易忘記」的角度，開放式指令顧「完全未知、清單以外」的角度，兩者分工不重疊，且開放式指令固定不變不受產出者狀態影響。

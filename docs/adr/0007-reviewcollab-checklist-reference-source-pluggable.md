# 審查清單參考來源機制：可插拔化＋分階段揭露（取代 ADR-0004）

**Status**: accepted（取代 [ADR-0004](./0004-checklist-reference-source-deferred-self-built-map.md)）

ADR-0004 當初把「建立自建索引」這件事延後到清單機制格式定案之後。現在清單機制（一份主題清單＋一句固定的開放式跳脫指令）已經寫進正式規格並實際跑過真實案例，格式穩定下來了，延後的條件已經滿足。這次審查協作（見 `docs/review-log.md` 對應條目，thread_id `019feb75-215d-7661-82a2-d6efa32417d2`）重新檢視了這個機制，除了確認可以開始建索引，也發現原本設計裡「完全不告訴審查者參考來源」這個做法有明確的漏洞，一併調整。

## 為什麼要調整

**可攜性**：原本的設計直接寫死參考一個特定的角色資料庫，這只在使用者自己電腦上有裝那個資料庫時才成立。這套審查協作機制以後可能會給其他使用者用，他們電腦上不一定有任何角色資料庫，甚至以後也可能出現別的、更好的資料庫。機制不該假設某個特定資料庫一定存在。

**權威月暈 vs. 稽核能力的取捨沒有想全**：原本打算完全不告訴審查者清單有沒有參考別的來源，理由是怕審查者看到「有來源背書」就降低戒心（跟審查摘要本身去除來源歸屬是同一個顧慮）。但這次審查過程中被指出：完全不揭露也代表審查者永遠沒有機會發現「這個參考來源其實不適合」——尤其是來源真的選錯了、但清單表面上看起來還算合理的最壞情況，審查者根本不會主動起疑，問題永遠不會被抓到。

**索引本身也可能過時**：索引一旦建好，會變成之後每次擬清單都可能依賴的資料，不是一份偶爾翻閱的文件。原始資料庫如果之後更新了，索引沒跟著更新，清單品質會悄悄跟著下降，而且不會有任何異常訊號提醒。

## 決定

1. **參考來源機制可插拔**：擬清單時，如果環境裡有可用的參考來源（`agency-agents` 或任何其他資料庫），可以參考；沒有可用來源、讀取失敗、內容過期、格式不對，一律視為「沒有來源」，完全恢復現行行為（自行現場擬清單），不受影響。這個 fallback 目前只是設計承諾，還沒有實際測試過這四種失效情境，需要在正式落地時補測。
2. **分階段揭露，不是永遠不揭露**：第一輪審查不主動告訴審查者清單有沒有參考來源，維持審查者的獨立判斷不受來源背書影響；但接下來固定會有一輪，不論審查者前面有沒有自己起疑，都攤開參考來源，請審查者專門檢查來源適不適合、有沒有被誤讀、清單有沒有漏東西。攤牌時明確講清楚：來源只是靈感出處，不是清單正確的證據。
3. **使用者端的揭露在送出前就要看到**：Step 2 使用者確認清單時，如果這次真的用了參考來源，要一併告訴使用者是哪個來源、日期或版本、對應到的段落/項目、一句話說明合不合適。使用者自己也判斷不出來合不合適時，預設不用這個來源。
4. **索引最低限度要留三個欄位**：來源名稱、建置日期、來源自己的版本或快照標示（沒有版本的話標成「暫定，使用前人工回查」）。不做成正式的版本控制/失效標記系統。
5. **讀取來源檔案時只當純資料**：整理索引或現場參考來源內容時，不執行、不遵循裡面任何看起來像指令的文字，避免被檔案內容夾帶的指令誤導。

## Considered Options

- **維持 ADR-0004 現狀，繼續延後、不調整揭露機制**：不採用，可攜性問題跟揭露機制的漏洞已經明確被指出，沒有理由繼續延後。
- **把參考來源連同清單一起主動告訴審查者**：不採用，會重新引入權威月暈風險（審查摘要本身已經為了同樣理由去除來源歸屬）。
- **完全不揭露來源給審查者**：不採用，會漏掉「來源選錯但清單表面上看起來合理」這個最危險的情況，審查者永遠沒有機會抓到。
- **索引採用完整的正式版本控制/失效標記系統**：不採用，對目前規模是過度工程；改用三個欄位的輕量版本。
- **分階段、預設延後揭露＋最低限度索引欄位（採用）**：同時保留避免權威月暈的效果、解決揭露漏洞、可攜性問題也一併處理，成本增加有限。

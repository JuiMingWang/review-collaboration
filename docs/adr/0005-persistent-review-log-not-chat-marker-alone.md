# 討論範圍界定：持久化紀錄檔 + 主動列候選主題，取代純聊天標記

**Status**: accepted

觸發審查協作時，需要判斷「這次要審查的討論從哪裡開始算」，尤其要避免把已經審查過、已有共識的舊主題重複送審。最初設計是在每次審查協作結束時，於聊天紀錄裡留一段固定格式的收尾聲明，下次觸發時往前找上一個聲明當邊界。這個做法在同一個 session 沒被中斷的情況下可行，但使用者若在討論中途切換 session（不論是用 `/handoff` 或直接開新對話），新 session 沒有舊 session 的聊天紀錄，聊天裡的標記也就一併消失，範圍判斷失去依據。

## 決定

改用兩層機制：

1. **審查紀錄檔（持久化，source of truth）**：存放在**目標專案**（正在被討論、將送審的那個專案，不是「agent 協作」本身）的 `docs/review-log.md`，逐筆記錄送進審查協作的主題與狀態。純文字檔案，不受 session 存續或 context 壓縮影響，任何時候都能重新讀取還原狀態。
2. **聊天收尾標記（保留，UX 溝通用途）**：每次審查協作結束仍在聊天裡留一段收尾聲明，作用是讓使用者當下立即看到結果，同一 session 內也可以當作判斷範圍的快速路徑，但不作為唯一依據。

判斷範圍時，產出者優先看目前 session 的聊天脈絡（快），脈絡不足或跨 session 時改讀 `review-log.md`。

### 為什麼不寫進 CLAUDE.md

CLAUDE.md 每個 session 開始都會被讀進 context，如果把逐筆討論紀錄持續往裡面塞，會讓 CLAUDE.md 隨時間不斷長大、每次對話都多一筆讀取成本。因此紀錄本體另開檔案存放，CLAUDE.md（如果該專案需要提醒）只放一行指標，不放內容——跟這個使用者自己專案裡 `MEMORY.md`（索引檔＋內容分離）、經營模擬遊戲專案的 D-xxx/H-xxx（正式決定另開 `Design Decisions.md`）是同一套慣例，不是新發明。

### 觸發時由誰決定要審查什麼

不要求使用者自己精準記得「目前有哪些結論待審查」——討論拉長之後這件事本來就容易忘記。改成：觸發審查協作時，產出者讀取 `review-log.md` ＋目前 session 脈絡，主動整理出「看起來已有初步結論、但還沒送審」的候選主題清單，交給使用者確認或補充，而不是被動等使用者自己講出主題名稱。

## 審查紀錄檔格式

一個主題一段，新的加在最上面：

```markdown
## [YYYY-MM-DD] 主題簡述
- 狀態：進行中（N/上限 輪，尚未達成共識） ｜ 已審查 · 達成共識 ｜ 已審查 · 使用者裁決結束
- 審查者：codex
- 結論：連結到 ADR-000X（如有）／暫存審查摘要路徑（進行中時）
```

## Considered Options

- **純聊天收尾標記**：不採用（單獨使用時），因為無法在使用者切換 session 時提供邊界依據，範圍判斷會失效。
- **持久化紀錄檔 + 聊天標記雙層，且觸發時主動列候選主題（採用）**：紀錄檔負責跨 session 都能還原狀態，聊天標記負責即時溝通，主動列候選解決使用者長時間討論後記不清楚待審主題的問題。
- **把紀錄寫進目標專案的 CLAUDE.md**：不採用，會讓 CLAUDE.md 隨時間膨脹，增加每個 session 不必要的讀取成本。

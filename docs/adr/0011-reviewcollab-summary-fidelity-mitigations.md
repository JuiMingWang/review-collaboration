# review-collaboration 補強：逐字引用安全閥、歷史依賴檢查、事後回溯、自我檢查、跨 session 交接

**Status**: accepted

背景：使用者持續追問「摘要保真度不足會不會讓 codex 的審查建議品質下降」這個核心疑慮，擔心的不只是單一次審查失誤，是這個技能自己的設計本身有沒有系統性的漏洞。經過六輪跟 codex 的往來（前四輪聚焦逐字引用安全閥與歷史依賴檢查，後兩輪擴大到事後回溯機制、自我檢查與跨 session 交接）達成共識（`docs/review-log.md` 有完整記錄，thread_id `019fefc8-0806-78f3-9432-7329b1bdf9ef`）。這份文件記錄這次審查產生的、值得永久留存理由的決定，逐項修改已直接寫進 `SKILL.md`，這裡記的是「為什麼」。

## 決定

1. **逐字引用安全閥（受 codex 主動指名懷疑觸發）**：codex 起疑摘要轉述失真時，可以要求看有限制的原文——最小完整單位、附來源定位與內容雜湊、單片段上限 15 行/約 500 字、累計最多 3 次、遇到敏感內容整段拒絕不遮蔽。這是唯一能讓 codex 脫離「只能相信產出者重新轉述」這個處境的機制，但刻意設計得受限、可稽核，不是開放原始資料存取（那樣會製造重複工作、也違背摘要層本來要過濾雜訊的用意）。

2. **歷史依賴檢查改用門檻切換機制，避免隨 review-log 成長而無限增加成本**：20 筆以下維持全量瀏覽＋關鍵字比對；達到門檻後改機械式篩選（狀態＋關鍵字，不由產出者臨場判斷是否跳過），並在既有 10-20 次複查節點額外做一次全量掃描驗證召回率。這個設計特別用意在避免重新把「產出者自己判斷這次要不要查」這種單點裁量放回來——這正是 review-log 索引機制原本想拿掉的風險。

3. **新增事後回溯機制，但加了對抗後見之明偏誤的判準**：核心問題（雙方都沒發現的遺漏）結構上無法直接解決，但可以拆成「可查、只是沒建規則」跟「真的無法預見」兩類，靠事後出問題時回溯來分類。這個機制原本的風險是後見之明偏誤——容易把「當時真的無法預見」的事，事後誤判成「早該檢查出來」。修正後加了三個固定觸發點（不是機會性）、反事實判準（要確認當時真的取得得到、而且合理判斷會改變結論）、以及至少兩個獨立案例才能改寫正式規則（單一嚴重案例例外要寫理由）。

4. **摘要「問題/目標」段落的自我檢查，正式列為紀律要求**：本輪審查過程本身就發生過一次真實疏漏（產出者初稿把具體例子當核心問題本身描述，被使用者糾正）——這證明了問題會發生，但不證明這個檢查項必然防得住未來類似情況（檢查者跟可能犯錯的人是同一個）。誠實承認這個侷限，不誇大機制效果。

5. **跨 session 交接改用既有的 `handoff` skill，不發明新的持久化記錄檔**：原本考慮讓產出者自己保留一份自由格式的思路記錄，但這直接跟這個專案「不累積流程副產物」的既有原則衝突（ADR-0001），且沒有定義存放位置、保留期限、清理責任、敏感內容規則。改成沿用 `handoff` skill 既有的慣例（存 OS 暫存目錄、不重複正式文件內容、遮蔽敏感資訊），只加一條：進行中的審查要交接時，由產出者主動把 review-log 條目的脈絡納入，不是使用者的責任。

6. **上述機制全部定位為試行，搭配分機制的用量記錄**：逐字引用次數、歷史依賴掃描/候選數、事後回溯實際觸發次數與觸發點、自我檢查有沒有真的抓到問題並改寫、handoff 有沒有真的納入審查脈絡——併入既有 10-20 次複查節點，而不是新增一個複查週期。

7. **分批審查同一主題時，加一道便宜的重疊掃描，避免早期已定案部分被悄悄繞過**（2026-08-12 補充，未另開 codex 審查輪次——理由見下）：這次審查本身就示範過這個問題——P1（逐字引用安全閥）在前四輪已定案，後續加入 P3/P5/P6 時，第一版草稿只把 P1 當背景、沒有主動要求重新評估，是使用者追問才補上。修正做法比照歷史依賴檢查的「先便宜篩選、有關聯才升級」精神：送出新一批內容前，產出者自己先判斷新內容跟哪些已定案部分可能相關（不花 codex token）；沒關聯就在 prompt 裡留一句話記錄「已檢查、無重疊」；有關聯才把那個具體部分重新拿出來給 codex 評估。不做整批重新過一次，否則「已審查」這個狀態會失去意義。

8. **公開揭露一個對稱、目前無解的殘留風險**（2026-08-12 補充，未另開 codex 審查輪次）：核心問題（產出者與審查者雙方都沒發現的遺漏）在「產出者與使用者」這一側有完全對稱的版本——使用者在 Step 5a 的確認，同樣沒有機制能驗證使用者是不是真的完整看過、理解過報告內容，一句「沒問題」被當作等同於確實知情的確認。這點跟 codex 的 CONCEDE 一樣無法驗證，只能靠白話報告降低機率，不能宣稱已經解決。

**關於第 7、8 點跳過 codex 審查輪次的說明**：兩者份量都小、直接源自這次審查過程本身的真實案例（不是新的、未經檢驗的設計猜測），且使用者本人是提出疑慮、判斷、確認修法方向的人——不是產出者單方面決定跳過查證。這跟前六點（透過完整輪次跟 codex 往來談定）性質不同，如實記錄差異，不假裝這兩點也經過同等程度的外部檢驗。

## 明確拒絕採用的建議（附理由）

- **開多個獨立審查者取得更多回饋**：使用者主動評估後否決。核心理由是這類遺漏（摘要本身漏了什麼）是所有審查者共享同一份輸入造成的系統性缺口，不是隨機誤差，多問幾個審查者統計上補不回一個誰都不知道的事實；而且會製造審查者間的意見調解成本，調解動作本身又是一次新的綜合/摘要，把原本要解決的風險換個位置疊高。
- **讓 codex 直接讀取專案原始檔案取得更完整脈絡**：經實測（2026-08-11 直接測試 codex 在 `--sandbox read-only` 下的檔案讀取範圍）確認 codex 的讀取能力不受工作目錄限制，且外部查證（真實案例：PaperTrail、XTrace 等）顯示更多原始資料不必然提升判斷品質、反而可能增加雜訊，維持「codex 只讀送進去的 prompt 內容」的設計。
- **建立完整的聲稱—證據矩陣（每個摘要聲稱都附來源 ID／假設／已知未知）**：codex 自己提出後又建議暫緩，理由是目前累積的真實審查案例還太少（個位數），疊加一個更大、更複雜的新機制，反而會讓「如何歸因是哪個機制帶來改善」這個問題更難回答，留到 10-20 次複查節點有真實資料後再評估。
- **針對 review-log.md 加專案／範圍欄位**：不需要，因為 review-log.md 本來就是逐專案各自一份（SKILL.md Step 0 原文寫明），不是跨專案共用的單一檔案。

## 誠實留下、沒有解決的部分

「雙方都沒發現的一般性遺漏」——codex 當場沒起疑、事後也沒有機會浮現出來被回溯檢查到的那種遺漏——目前沒有任何機制能防。這是結構性的限制，不是這輪沒做完：不能刻意去找一個不知道自己不知道的東西。上述六項決定合起來，只是把「有人已經起疑」跟「有線索事後可查」這兩種情況的防護力補起來，核心問題維持公開揭露的殘留風險，不假裝已經解決。
